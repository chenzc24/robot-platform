## ESP32

The old device ran `tcp_v2_l3`. WebREPL's port was reachable, but its HTTP
upgrade timed out before authentication or file access. The operator connected
USB; COM7 was used to inspect, back up, and replace the runtime. Firmware
remains MicroPython 1.27 on ESP32_GENERIC_S3 with octal SPIRAM.

All root Python files were backed up before replacement. The candidate was
first verified in `tcp_v3_l2` without creating a CAN runtime: WELCOME, PONG,
and STATE passed with `motion_permitted=false`. The final configuration was
then uploaded, downloaded, and hash-compared before reset.

Final wireless application responses, also verified in a later fresh session:

```text
HELLO  -> WELCOME  version=3 sequence=1 protocol=3
PING   -> PONG     version=3 sequence=2 protocol=3
STATUS -> STATE    version=3 sequence=3
service_state=ready
chassis_state=disabled
authenticated=true
motion_permitted=true
hold_remaining_ms=0
last_error=none
```

`motion_permitted=true` means the runtime supports explicit Enable, not that
motion is enabled. The limits are the previously approved 600 mm/s and
800 mrad/s. CAN pins/rate, Wi-Fi settings, and runtime credential were preserved.

The operator confirmed stationary, clear-area deployment. No Enable, velocity,
jog, or gripper request was sent. CAN-backed startup/session cleanup can send
zero/disable output; this is not a claim of zero CAN traffic. No motion test
was performed.

The probe loaded the preserved credential from the ignored device backup.
The PC's `ROBOT_CHASSIS_CREDENTIAL` environment variable was absent, and the
local ESP32 secrets file lacked `RUNTIME_CREDENTIAL`. Probe success therefore
does not establish credential readiness for a separately launched UI/CLI.
Supply the preserved credential through the configured local secret mechanism
before that launch; do not print or commit it. No secret was rotated or written
to a system-wide environment variable.

WebREPL recovery remains unverified after the final reset. A working runtime
TCP protocol does not establish wireless maintenance responsiveness.

## MaixCam

SSH identity/connectivity were verified. Arm/video directories were backed up
before replacement. Sources were staged in
`/root/robot-platform/releases/20260903-adf4af2`, then activated in the existing
`/root/robot-platform/arm` and `/root/robot-platform/video` directories. All 17
active files matched staged SHA256 hashes; all 13 Python files compiled on
the device without hardware imports.

The local gateway configuration uses the previously requested `YOLO_MODE=True`.
UART0, 115200 baud, and endpoint port 8780 are unchanged. The old one-use
admission file remains on disk but is not used by the new server.

The operator explicitly authorized stopping `num`. Its exact process identity
was checked, then SIGTERM stopped it. Its source hash remained unchanged;
no app code or auto-start configuration was edited. Launcher ownership was
restored before project startup.

Activation exposed two regressions in the modular video service: buffered
stdout hid the ready event from `start.sh`, and native MaixPy initialization
overrode the earlier SIGTERM handler. Video decoded despite the reported
startup timeout. The owned initial video process exited via SIGINT.

The fix launches Python unbuffered and installs stop handlers after backend
initialization. Timeout cleanup now retains the PID file if its verified
process is still alive. The two changed files were backed up, deployed, and
hash-verified. Readiness succeeded after 8 seconds; SIGTERM stop returned
`RTSP_STOPPED`; restart succeeded after 9 seconds.

Final video probe, with the arm gateway running: H.264, 1280 x 720, nominal
20 fps; 101 frames decoded in 6.078 seconds, first frame after 2.343 seconds.
Media timestamps were unavailable, so no measured media FPS is claimed.
The final video PID was 1336; the arm gateway PID was 1415, sole UART0 owner.
These are observation-time identifiers, not reusable process-control targets.
The guard intentionally suspends the verified launcher supervisor while the
arm service owns UART0 and restores it on guard exit.

MaixCam ICMP PING returned 2/2 replies; SSH and ports 8554/8780 were available.
`robot arm ping --arm-host <discovered-address> --json` reached the gateway,
which initially returned `FAULT / response_timeout` before the operator started
the controller project. After the operator reported it running, downstream PING
and measured STATUS passed as recorded below. No TCP232 setting was changed.

This agent did not modify controller code, taught points, TCP232, or LAN2.
The operator subsequently started the generated controller project. The
normalized measured-feedback route passed L2; raw vendor return-container
types and in-motion sampling were not captured. MaixCam auto-start was not
configured; existing `num` auto-start is unchanged.
